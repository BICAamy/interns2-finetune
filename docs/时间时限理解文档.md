# 真实机械臂项目时间机制与超时阈值梳理

## 1. 总体结论

当前项目中涉及的“时间”可以分成 4 类：

| 类别 | 作用 | 当前主要阈值 |
|---|---|---:|
| 真机状态新鲜度 | 判断 10004 状态还能不能相信 | `250 ms` |
| Mac ↔ Server 会话存活 | 判断 Mac gateway 是否还在线 | `1500 ms` |
| 真机运动生命周期 | WayPoint 从发送到开始、完成的时限 | `500 ms / 5 s / 10 s` |
| 停止生命周期 | Stop 请求送达与真实停止确认 | `500 ms / 3 s` |

最重要的是：

```text
state_stale_ms
```

管的是**状态数据还能不能信**；

```text
response_ms
startup_ms
motion_ms
stop_delivery_ms
stop_ack_ms
```

管的是**一次运动命令的执行过程**。

这两类不能混在一起。

---

# 2. 一帧 10004 数据中涉及的两个时间

机械臂通过 `10004` 持续发送 DataSheet。

当前现场观察频率约为：

```text
20 Hz
≈ 每 50 ms 一帧
```

注意：**50 ms 是现场观察到的周期，不是代码硬性规定必须每 50 ms 一帧。**

每个 `DatasheetSample` 中有两个非常重要的时间字段：

```text
source_timestamp_ms
received_monotonic_ns
```

它们来自不同机器。

## 2.1 `source_timestamp_ms`

来源：

```text
E05-Pro 控制器
```

表示：

> 机械臂控制器给这帧状态附带的源时间戳。

例如可能出现：

```text
Frame 1   source_timestamp_ms = 1000
Frame 2   source_timestamp_ms = 1000
Frame 3   source_timestamp_ms = 1000
Frame 4   source_timestamp_ms = 1050
Frame 5   source_timestamp_ms = 1050
Frame 6   source_timestamp_ms = 1100
```

目前现场已经观察到：10004 虽然约 20 Hz 推流，但 `Stamp` 不一定每帧更新。

所以代码允许 source timestamp 短时间重复。

---

## 2.2 `received_monotonic_ns`

来源：

```text
Mac
```

表示：

> Mac 实际收到这帧 DataSheet 时，本机 `time.monotonic_ns()` 的值。

例如：

```text
机械臂产生：
source_timestamp_ms = 1050

Mac 收到：
received_monotonic_ns = 9384012345000
```

这两个时间不能直接做：

```text
Mac 时间 - 机械臂时间
```

因为它们属于不同机器、不同计时基准。

当前项目因此只在**同一台机器内部**使用 monotonic 时间计算时间间隔。

---

# 3. `state_stale_ms = 250` 的真正含义

当前配置：

```yaml
state_stale_ms: 250
```

这个 250 ms 被两个 watchdog 使用：

```text
StateWatchdog
SourceStampWatchdog
```

虽然阈值一样，但检查的是两种不同故障。

---

# 4. StateWatchdog：Mac 手里的状态是不是太旧了

代码逻辑可以简化成：

```python
age_ms =
    Mac当前monotonic时间
    -
    sample.received_monotonic_ns

fresh = age_ms <= 250
```

也就是：

> 最后一帧状态从 Mac 收到之后，已经过去多久。

例如 Mac 在：

```text
t = 1000 ms
```

收到一帧。

在：

```text
t = 1150 ms
```

检查：

```text
age = 150 ms

150 <= 250

→ fresh
```

在：

```text
t = 1300 ms
```

检查：

```text
age = 300 ms

300 > 250

→ stale
```

所以：

```text
StateWatchdog
```

主要防止：

```text
10004 停流
Mac 很久没有收到新的真实状态
```

源码中的判断就是根据 Mac 本机收到状态后的 elapsed time 完成的。

---

# 5. “250 ms ≈ 丢 5 帧”应该怎么理解

当前现场大约：

```text
50 ms / frame
```

所以：

```text
250 / 50 ≈ 5
```

因此配置中的注释：

```yaml
state_stale_ms: 250
# 50 ms 一帧，连续约 5 帧未收到即标为过期
```

可以帮助理解，但源码实际没有：

```python
missed_frames >= 5
```

这样的计数。

真实判断是：

```text
最后收到的有效状态
距离现在
是否超过 250 ms
```

所以更准确的描述是：

> 最后一帧状态超过 250 ms 没有被新状态替代，就认为 stale；按照当前约 20 Hz 的推流速度，大致相当于连续约 5 个帧周期没有收到新状态。

---

# 6. SourceStampWatchdog：机械臂的源时间戳有没有卡住

另一个：

```text
SourceStampWatchdog
```

检查机械臂自己的：

```text
source_timestamp_ms
```

它有两个规则。

第一条：

```text
source timestamp 不能倒退
```

例如：

```text
1000
1050
1100
900
```

出现：

```text
1100 → 900
```

立即报错。

第二条：

```text
timestamp 可以重复，
但不能超过 250 ms 一直不推进
```

例如：

```text
t=0 ms      stamp=1000
t=50 ms     stamp=1000
t=100 ms    stamp=1000
t=150 ms    stamp=1050
```

正常。

但是：

```text
t=0 ms      stamp=1000
t=50 ms     stamp=1000
t=100 ms    stamp=1000
t=150 ms    stamp=1000
t=200 ms    stamp=1000
t=300 ms    stamp=1000
```

超过 250 ms 仍没有推进：

```text
→ DataSheet source timestamp stopped advancing
```

源码明确允许重复 stamp，但如果它超过 stale 阈值不再向前推进就报错。

---

# 7. 两个 Watchdog 的区别

这是状态时间机制里最重要的一张表：

| 检查器 | 检查对象 | 防止的问题 |
|---|---|---|
| `StateWatchdog` | Mac 的 `received_monotonic_ns` | 10004 已经很久没收到新状态 |
| `SourceStampWatchdog` | 机械臂的 `source_timestamp_ms` | TCP 还在收包，但控制器 source timestamp 已经卡住 |

典型故障：

```text
Mac 一直收到 TCP 包：

t=0      stamp=1000
t=50     stamp=1000
t=100    stamp=1000
t=150    stamp=1000
t=300    stamp=1000
```

对于：

```text
StateWatchdog
```

每个包都是刚收到的，因此：

```text
age ≈ 0
```

看起来仍然 fresh。

但是：

```text
SourceStampWatchdog
```

会发现：

```text
机械臂 source timestamp
已经 300 ms 没有推进

→ fault
```

所以两个检查必须同时存在。

---

# 8. 10004 socket 本身还有一个 250 ms timeout

Step 11 的 `LocalDataSheetSampler` 创建：

```python
DatasheetClient(
    ...,
    timeout_s=0.25,
)
```

这里：

```text
0.25 s = 250 ms
```

但它和：

```text
state_stale_ms = 250
```

不是一个概念。

区别如下：

| 参数 | 意义 |
|---|---|
| socket `timeout_s=0.25` | 一次 `recv()` 最多阻塞多久 |
| `state_stale_ms=250` | 已经收到的最后状态最多还能被相信多久 |

只是当前两个值恰好都为：

```text
250 ms
```

---

# 9. 10004 第一次启动还有一个 3 秒时限

Step 11 的 `LocalDataSheetSampler.start()` 启动后台线程以后，会等待第一帧有效 DataSheet。

最大等待：

```text
3 秒
```

如果 3 秒都没有第一帧：

```text
TimeoutError:
no initial real DataSheet sample
```

这是代码硬编码的时间。

不属于 YAML 的 `deadlines:`。

---

# 10. 首次运动前还有 5 秒静止观察

Step 11 定义：

```text
STATIONARY_OBSERVATION_S = 5.0
```

在真正发送 WayPoint 之前，连续观察：

```text
5 秒
```

期间大约每：

```text
50 ms
```

读取一次最新状态。

因此大约进行：

```text
5 / 0.05 = 100 次检查
```

这 5 秒期间机器人必须持续满足：

```text
moving = False
FSM = 33 READY
enabled = True
InPos = True
没有 pause
没有 free-drive
没有 force-control
mode 不变化

位置漂移 ≤ 0.25 mm
关节漂移 ≤ 0.1°
姿态漂移 ≤ 0.1°
```

这里的：

```text
5 秒
```

是**运动前稳定观察窗口**，与 250 ms stale deadline 没有关系。

# 11. 运动命令的六个 deadline

当前配置：

```yaml
deadlines:
  state_stale_ms: 250
  response_ms: 3000
  startup_ms: 5000
  motion_ms: 120000
  stop_delivery_ms: 500
  stop_ack_ms: 3000
```

它们可以按运动生命周期排列：

```text
状态是否可信
state_stale_ms
      │
      ▼
发送 WayPoint
      │
      ├── response_ms
      ▼
控制器接受命令
      │
      ├── startup_ms
      ▼
看到 moving=True
      │
      ├── motion_ms
      ▼
运动完成
```

如果中途发生异常：

```text
request_stop()
      │
      ├── stop_delivery_ms
      ▼
GrpStop 是否送达
      │
      ├── stop_ack_ms
      ▼
实际反馈确认机器人停止
```

---

# 12. `response_ms = 3000`

配置意义：

> 发送 10003 命令以后，最多允许等待控制器协议回复的时间。

配置值：

```text
3000 ms = 3 秒
```

但是 Step 11 第一次真机运动实际上使用更严格的 socket timeout：

```python
min(
    response_ms,
    stop_delivery_ms,
    500
)
```

当前：

```text
response_ms      = 3000
stop_delivery_ms = 500
hard cap         = 500

min = 500
```

所以当前 Step 11：

```text
实际 10003 socket timeout = 500 ms
```

因此：

```text
YAML 上限：3 秒
Step 11 实际：0.5 秒
```

---

# 13. `startup_ms = 5000`

意义：

> WayPoint 发出以后，最多允许多久还没有看到机器人真正开始运动。

当前：

```text
5000 ms = 5 秒
```

代码记录：

```text
sent_monotonic_ns
```

之后不断检查真实反馈。

如果 5 秒以内出现：

```text
moving=True
```

则认为：

```text
运动已经真正开始
```

如果：

```text
5 秒过去
moving_seen 仍然为 False
```

则：

```text
startup timeout
→ request_stop()
```

注意：

```text
WayPoint OK
```

只代表：

```text
控制器接受了请求
```

它不代表机器人已经开始运动。

---

# 14. `motion_ms = 120000`

YAML 配置意义：

```text
整个运动最多允许 120000 ms
= 120 秒
= 2 分钟
```

但是 Step 11 首次真机运动又有一个更严格的硬限制：

```text
FIRST_MOTION_MOTION_TIMEOUT_MS = 10000
```

构建实际 timing 时：

```python
motion_ms = min(
    config.deadlines.motion_ms,
    10000
)
```

因此当前：

```text
min(120000, 10000)
= 10000 ms
```

所以：

```text
YAML 总体上限：120 秒
Step 11 首动实际上限：10 秒
```

当前首动只有：

```text
1 mm
2 mm/s
```

理论运动主体约：

```text
0.5 秒
```

所以 10 秒已经是非常宽松的异常保护上限。

---

# 15. `stop_delivery_ms = 500`

意义：

> 发送软件停止 `GrpStop` 后，最多允许多久确认这个请求有没有成功送到/得到协议回复。

当前：

```text
500 ms
```

重点：

```text
GrpStop OK
```

只能说明：

```text
停止请求送达了
```

不能说明：

```text
机器人已经物理停止
```

所以：

```text
stop delivery
```

和：

```text
motion stopped
```

必须分开。

---

# 16. `stop_ack_ms = 3000`

意义：

> Stop 请求发出以后，最多允许多久等待真实状态确认机器人已经停住。

当前：

```text
3000 ms = 3 秒
```

代码要求真实反馈满足：

```text
moving = False
FSM = 33 READY
brakes_released = False
```

而且必须：

```text
连续 2 个 fresh sample
```

才真正标记：

```text
stopped
```

因此：

```text
GrpStop OK
        ↓
还不能叫 stopped
        ↓
继续观察真实反馈
        ↓
连续两个 fresh nonmoving READY sample
        ↓
stopped
```

如果 3 秒过去仍然无法确认：

```text
stop_unconfirmed
```

程序只能说：

> Stop 请求可能已经送达，但无法证明机器人已经停止。

# 18. Server 端还有另一套会话时间

服务器的 `GatewaySessionManager` 还有：

```text
gateway_timeout_ms = 1500
transit_budget_ms = 100
```

它们和机械臂运动 deadline 无关。

## `gateway_timeout_ms = 1500`

表示：

> Server 超过 1.5 秒没有收到 Mac 的有效 state 或 heartbeat，就认为 gateway 会话已经失效。

因此：

```text
Mac 完全没有任何消息 > 1.5s

→ gateway disconnected
```

---

## `transit_budget_ms = 100`

服务器无法安全地做：

```text
Server monotonic - Mac monotonic
```

因为两台机器的 monotonic 时钟没有共同原点。

所以 Server 保守地给：

```text
Mac → Server 网络传输
```

预留：

```text
100 ms
```

服务器上的状态年龄计算：

```text
Server认为的状态年龄
=
Mac发送时状态已经有多老
+
100ms 网络传输预算
+
状态到Server后又停留了多久
```

例如：

```text
Mac发送时：
状态 age = 30 ms

网络预算：
100 ms

Server收到后又过了：
50 ms
```

那么：

```text
Server age
= 30 + 100 + 50
= 180 ms
```

因为：

```text
180 < 250
```

所以仍然：

```text
FRESH
```

再过 80 ms：

```text
30 + 100 + 130
= 260 ms
```

则：

```text
STALE
```

假设：

```text
T = 0
发送 WayPoint

T = 0.1s
WayPoint OK

T = 0.2s
moving=True

T = 0.35s
收到最后一帧有效状态
```

```text
T ≈ 0.60s
```

最后一帧已经：

```text
0.60 - 0.35
= 0.25s
= 250ms
```

```text
state stale
```

运动 watchdog 不再相信当前状态，并执行：

```text

```

```text
T = 0.61s

确认 Stop 是否成功送达
```

如果收到：

```text
GrpStop OK
```

状态只能变成：

```text
stop_delivery = sent
```

仍然继续观察真实机器人。

例如：

```text
T = 0.80s
fresh sample：
moving=False
FSM=33
brakes held

T = 0.85s
第二个 fresh sample：
moving=False
FSM=33
brakes held
```

这时才能：

```text
stopped
```

如果 Stop 发送之后：

```text
3 秒
```

仍然没有得到足够的真实反馈：

```text
stop_unconfirmed
```

绝不能把：

```text
GrpStop OK
```

直接当成：

```text

```

## 22. 一句话记忆

整个项目的时间机制可以压缩成：

```text
250ms
= 状态还能不能信

500ms
= 当前 Step11 TCP 命令/Stop 请求最多等多久回复

5s
= WayPoint 后必须开始运动

10s
= Step11 第一次运动整体最长时间

3s
= Stop 后必须确认真实机器人停住

1.5s
= Server 多久听不到 Mac 就认为 gateway 掉线
```

而 YAML 中的：

```text
response_ms = 3000
motion_ms = 120000
```

是总体配置上限；当前第一次真机运动又分别收紧成了：

```text
response → 500ms
motion → 10s
```

这就是当前源码真正执行的时间约束。

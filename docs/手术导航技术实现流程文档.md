> 文档类型：项目施工手册 / 唯一实施顺序

## 1. 本文怎么使用

本文不是架构设想，而是后续开发时逐步执行的施工顺序。每个 Step 都包含：

- 目标；
- 前置条件；
- 需要修改或新增的文件；
- 服务器执行命令；
- 测试方法；
- 完成标准；
- 不满足完成标准时的停止条件。

执行规则：

1. 严格按 Step 顺序实施，不同时跨多个 Step 大改；
2. 每完成一个 Step，先运行该 Step 的测试并记录结果；
3. 验收失败时不进入下一 Step；
4. 每个 Step 使用独立 Git 提交，保证可以回溯；
5. 实际文件名、端口或依赖若发生变化，先更新本文再继续开发；
6. 本地只负责修改代码，GPU、Docker 和 SOFA 相关命令由用户在服务器执行；
7. 任何文档中的占位符，例如 `<IMAGE_NAME>`，必须替换后再运行，不能原样执行；
8. 禁止为了“先跑通”而绕过 Schema、状态机和到达入点检查。

### 1.1 我们负责的工作

- 删除 NavGPT 和对应 DeepSeek 适配；
- 重构 InternS2 智能体运行时；
- 将非结构化输入解析成统一结构化任务；
- 建立机械臂工具和穿刺路径规划工具的接口；
- 使用 Mock 路径规划工具打通调用链；
- 拉取并固定 LapGym 的核心代码 `sofa_env`；
- 建立机械臂/针尖移动到入点的连续仿真；
- 支持“往上抬一点”等相对移动；
- 建立 FastAPI + React 网页；
- 从本地浏览器观看服务器仿真；
- 接入语音和固定手势；
- 实现“急停 > 停止 > 语音 > 手势”的仲裁；
- 建立四服务容器架构；
- 编写测试、启动脚本和部署说明。

### 1.2 不属于我们的工作

- 不进行 InternS2 LoRA 微调；
- 不构建或清洗微调数据集；
- 不研发穿刺路径规划算法；
- 不定义学长路径规划算法内部的控制策略；
- 当前不执行路径规划输出的穿刺控制数值；
- 当前不仿真针从入点穿刺到靶点；
- 当前不实现针体、软组织、接触力和穿刺物理；
- 当前不接入真实机械臂。

InternS2 推理服务被视为已有外部能力；路径规划算法被视为学长后续交付的外部能力。我们只开发两者之间的智能体、工具适配、定位仿真、网页和部署链路。

## 2. 最终交付结果

完成本文的必做步骤后，系统应具备以下效果：

### 2.1 完整坐标任务

```text
用户输入非结构化文本 / 语音
  → InternS2 提取入点、靶点和任务意图
  → 智能体运行时校验结构化 JSON
  → 调用机械臂定位工具
  → 网页显示仿真机械臂连续移动到入点
  → 验证机械臂确实到达入点
  → 调用路径规划适配服务
  → 当前由 Mock 或学长工具返回规划数值
  → 网页显示路径规划状态和返回结果
  → 当前任务在此结束，不执行仿真穿刺
```

### 2.2 相对移动任务

```text
用户输入“往上抬一点”或做出向上手势
  → InternS2 输出相对移动任务
  → 智能体运行时应用默认步长
  → 调用机械臂相对移动工具
  → 网页显示机械臂沿基座坐标系 +Z 连续移动
  → 移动完成，不调用路径规划
```

### 2.3 最终运行的四个服务

| 服务 | 容器名 | 内部端口 | 职责 |
|---|---|---:|---|
| InternS2 推理 | `interns2-inference` 或现有 `xl_interns2_lmdeploy` | 23333 | OpenAI-compatible 多模态推理 |
| 智能体与网页 | `agent-web` | 8000 | 智能体、会话、网页、语音/手势入口、工具编排 |
| 机械臂仿真 | `robot-simulation` | 8001 | SOFA/LapGym、运动控制、遥测和离屏渲染 |
| 路径规划适配 | `planner-adapter` | 8002 | 当前运行 Mock，以后转发到学长工具 |

浏览器只访问 `agent-web`。其他服务默认只在 Docker 内部网络开放，避免前端绕过智能体运行时直接控制机械臂。

### 6.3 技术实现

使用 Pydantic v2 定义并校验以下模型：

- `Point3D`；
- `RelativeMotion`；
- `ParsedCommand`；
- `RobotState`；
- `MoveToEntryRequest` / `MoveToEntryResult`；
- `MoveRelativeRequest` / `MoveRelativeResult`；
- `PlanPunctureRequest` / `PlanPunctureResult`；
- `ToolEvent`；
- `ErrorResponse`。

固定约束：

- 意图枚举：`puncture`、`move_to_entry`、`move_relative`、`stop`、`emergency_stop`、`clarify`；
- 对外距离单位统一为 `mm`；
- 第一版默认坐标系为 `robot_base`；
- `puncture` 必须有入点和靶点；
- `move_to_entry` 必须有入点；
- `move_relative` 必须有相对移动参数；
- 所有服务返回稳定错误码；
- 所有请求带 `schema_version`、`request_id` 或 `command_id`。

### 6.4 Mock 接口

此时不接 SOFA，先实现内存版：

- `FakeRobotController`：记录当前 TCP，可以模拟成功、不可达和超时；
- `FakePuncturePlannerClient`：记录调用次数，可以模拟成功、失败和超时。

这一阶段的关键测试不是“能移动”，而是流程约束：

```text
移动到入点失败 → planner 调用次数必须为 0
相对移动成功   → planner 调用次数必须为 0
完整穿刺且到达入点 → planner 调用次数必须为 1
```

## 7. Step 3：拉取并固定 LapGym/`sofa_env`

### 7.1 目标

LapGym 是框架和论文名称，实际需要开发和调用的核心仓库是 [`ScheiklP/sofa_env`](https://github.com/ScheiklP/sofa_env)。上游 README 当前推荐 Python 3.10，安装后使用 `controllable_object_example` 测试。

### 7.2 引入方式

将上游固定提交的跟踪文件作为普通源码快照纳入主仓库，不使用 Git submodule。这样服务器仅需执行普通 `git pull`，不依赖子模块初始化。

在项目根目录执行：

```bash
git clone https://github.com/ScheiklP/sofa_env.git /tmp/sofa_env-upstream
git -C /tmp/sofa_env-upstream checkout 85bf7e05dd088b824794dda0046679df13b13e6e
git -C /tmp/sofa_env-upstream rev-parse HEAD
```

将该提交的全部跟踪文件复制到 `third_party/sofa_env`，但不得带入上游 `.git` 目录。引入的确切提交和运行约束记录在 `docs/第三方依赖.md`。

提交快照后，服务器拉取方式为：

```bash
cd ~/interns2-finetune
git pull
```

### 7.3 版本管理规则

## 8. Step 4：建立 SOFA/LapGym 仿真镜像并跑通上游示例

### 8.1 目标

先证明服务器可以加载 SOFA、SofaPython3 和 `sofa_env`，再开发自己的场景。此时不接 InternS2。

### 8.2 版本基线

固定的 `sofa_env` 上游安装逻辑要求 Python 3.10 和 `x86_64`，并使用预构建 SOFA 二进制。具体 SOFA 版本以固定源码快照的 `setup.py` 为准，不能只看最新 SOFA 官网版本。

因此仿真必须使用独立镜像，不在现有 LMDeploy 容器中安装 SOFA。

### 8.3 新增文件

```text

simulation/scripts/check_sofa_imports.py
simulation/scripts/check_upstream_env.py
```

仿真镜像建议基于 Ubuntu 22.04 / Python 3.10，并安装：

- `wget`、`unzip`、`git`；
- Python 3.10、开发头文件和 pip；
- OpenGL/EGL 常用运行库；
- `xvfb` 作为兼容性回退；
- 固定源码快照中的 `sofa_env`；
- 本项目仿真服务依赖。

不要一开始手动从源码编译最新 SOFA。先按固定 `sofa_env` 的推荐预编译二进制路线验证；只有该路线与服务器不兼容时才记录原因并切换到手动构建。

## 11. Step 7：重构 InternS2 非结构化数据解析

### 11.1 目标

让 InternS2 将用户的文本、图片或预处理后的语音/手势信息转换成统一 `ParsedCommand`，不直接输出底层轨迹。

### 11.2 推荐调用方式

继续使用现有 LMDeploy 的 OpenAI-compatible API 和 InternS2 tool-call parser。向模型只暴露一个高层结构化入口，例如：

```text

```

该工具参数就是 `ParsedCommand`。模型不直接获得仿真 HTTP 地址，也不直接获得路径规划服务地址。确定性的运行时接收 `ParsedCommand` 后再决定工具顺序。

这样可以避免模型在同一轮同时调用“移动到入点”和“路径规划”，也可以强制执行“先确认到达入点”的规则。

### 11.3 需要实现

- 文本输入；
- 可选图像输入；

- tool arguments 的 JSON 解析；
- Pydantic 二次校验和规范化；
- 单位、坐标系和默认相对步长处理；
- 信息不足时的澄清回复；
- 模型超时、无 tool call、非法 JSON 的稳定错误处理。

### 11.4 Prompt 必须包含的规则

- 不得编造入点或靶点；
- 不得把二维像素当成三维坐标；
- 完整穿刺任务必须提取入点和靶点；
- 只移动到入点时不要求靶点；
- “往上抬一点”属于相对移动；
- 第一版“上”映射到 `robot_base +Z`；
- “一点”使用配置的默认步长；
- 不生成关节角、力矩或穿刺轨迹；
- 缺少必要信息时选择 `clarify`；
- 停止和急停使用专门意图。

- 明确入点和靶点；

- 方向和明确距离；

## 12. Step 8：实现确定性的任务状态机和工具编排

### 12.1 目标

把 InternS2 的结构化结果转换成受约束的工具执行流程。工具调用顺序由代码状态机控制，不由大模型自由排列。

### 12.2 状态机

```text
IDLE
  → PARSING
  → VALIDATING
  ├→ CLARIFICATION_REQUIRED
  ├→ EXECUTING_RELATIVE → COMPLETED
  └→ MOVING_TO_ENTRY
        ├→ FAILED
        └→ AT_ENTRY
              ├→ COMPLETED（move_to_entry）
              └→ PATH_PLANNING（puncture）
                    ├→ PLANNER_UNAVAILABLE
                    ├→ PLAN_FAILED
                    └→ PLAN_READY

任意运动状态 → STOPPED
任意状态 → ESTOP
```

当前状态机没有 `PUNCTURE_EXECUTING`。

### 12.3 编排逻辑

#### `move_relative`

```text
校验相对位移
  → 调用 robot.move_relative
  → 等待成功或失败
  → 返回用户
```

#### `move_to_entry`

```text
校验入点
  → 调用 robot.move_to_entry
  → 查询最终 TCP
  → 验证位置误差
  → 到达后结束
```

#### `puncture`

```text
校验入点和靶点
  → 调用 robot.move_to_entry
  → 等待工具返回
  → 再次查询 TCP 并独立计算位置误差
  → 只有 reached=true 且误差在阈值内
      → 调用 planner.plan(entry, target)
  → 显示规划结果
  → 不执行控制数值
```

不能只信任机械臂工具返回的 `reached=true`；运行时需要根据最终 TCP 和入点再次计算误差。

### 12.4 必须测试的不变量

- 定位失败时 planner 调用次数为 0；
- 最终误差超标时 planner 调用次数为 0；
- 相对移动时 planner 调用次数为 0；
- `move_to_entry` 时 planner 调用次数为 0；
- `puncture` 成功到达入点后 planner 调用次数为 1；
- 急停后 planner 调用次数为 0；
- 重复 `command_id` 不会重复运动；
- 当前执行中不接受第二条普通运动命令。

### 12.5 完成标准

- 所有工具顺序由确定性代码控制；
- InternS2 不能绕过状态机；
- 失败和停止可以正确阻断后续调用；
- 状态变化都有事件记录；
- 用户回复准确区分“到达入点”“规划完成”和“穿刺完成”。

推荐提交：

```text

```

### 16.2 第一版视频方案

## 17. Step 13：接入语音输入

### 17.1 目标

## 18. Step 14：接入手势与多输入仲裁

### 18.1 目标

使用电脑摄像头识别固定方向和停止手势，并保证语音与手势同时出现时语音优先。

### 18.2 手势实现

第一版在浏览器使用 MediaPipe Hands 或同类 Web 模型：

```text
本地摄像头
  → 手部关键点
  → 固定手势分类
  → 连续多帧稳定性检查
  → gesture candidate
  → agent-web 仲裁器
  → InternS2 / 结构化任务
  → 相对移动工具
```

优点：

- 原始摄像头视频无需持续上传服务器；
- 降低带宽；
- 不增加容器；
- 页面可以即时显示关键点和置信度。

固定手势只表示方向、停止或急停。手势指向屏幕某处不等于提供三维入点，当前不得由二维手势推断穿刺坐标。

### 18.3 初始手势集合

- 上；
- 下；
- 左；
- 右；
- 前；
- 后；
- 停止；
- 急停。

方向手势转换成候选语义后，InternS2 输出统一 `move_relative`；停止和急停直接进入快速控制通道。

### 18.4 仲裁器

服务端最终优先级：

```text
急停 > 停止 > 普通语音 > 普通手势
```

初始配置：

- 手势检测 10～15 FPS；
- 普通手势连续稳定 8 帧；
- 普通手势置信度不低于 0.85；
- 停止手势阈值可适当降低；
- 同一手势触发后冷却 1 秒；
- 语音/手势冲突窗口 1.5 秒；
- VAD 检测到正在说话时暂停提交普通手势。

浏览器只生成候选输入，最终仲裁必须在 `agent-web` 服务端完成，不能完全依赖前端状态。

### 18.5 必测场景

- 单个上移手势只触发一次；
- 持续保持不会连续移动；
- 松开、冷却后可以再次触发；
- 语音“向下”与手势“向上”冲突时执行语音；
- 任意普通语音执行中，急停手势仍能抢占；
- 摄像头丢失不会产生随机命令；
- 页面切到后台后不会积压并补执行旧手势。

### 18.6 完成标准

- 固定手势可以驱动相对移动；
- 语音优先级正确；
- 停止和急停可以抢占；
- 手势误触发率可测量；
- 相机权限拒绝不影响文本和语音功能。

推荐提交：

```text
feat: add gesture commands and multimodal arbitration
```

### 19.6 健康检查

| 服务 | 健康检查 |
|---|---|
| InternS2 | `GET /v1/models` |

| robot-simulation | `GET /health`，仿真 worker 存活 |
| planner-adapter | `GET /health`，显示当前 provider |

`depends_on` 只控制启动顺序，不能代替应用层重试。agent 在下游尚未就绪时应显示“服务准备中”，不能崩溃退出。

## 24. 开发过程中禁止的捷径

1. 禁止重新引入 NavGPT、R2R 或 viewpoint；
2. 禁止为了演示而让 InternS2 直接生成关节角；
3. 禁止在模型回复中用字符串正则直接拼接机器人控制命令；
4. 禁止定位失败后仍调用 planner；
5. 禁止把 Mock 直线预览称为真实路径规划结果；
6. 禁止把 planner 未知输出直接执行；
7. 禁止把操作者相机二维像素当作机器人三维坐标；
8. 禁止在现有 LMDeploy 容器中混装 SOFA；
9. 禁止在没有固定 commit 的情况下追随 `sofa_env/main`；
10. 禁止只测试正常路径而不测试急停、超时和断连；
11. 禁止网页直接访问仿真控制接口绕过 agent；
12. 禁止当前页面显示“穿刺完成”；
13. 禁止默认开启真实机械臂或穿刺执行；
14. 禁止因容器问题使用会删除卷的命令清理环境。
